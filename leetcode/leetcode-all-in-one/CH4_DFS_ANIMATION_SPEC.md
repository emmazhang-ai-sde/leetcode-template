## 1. 为什么要单独写这一份

前面九章的动画，看的是数据怎么变：指针往哪挪、队列进出了什么、堆顶换成了谁。
第四章不一样，第四章难的不是数据，是**同一段代码被反复执行，你分不清这一遍是谁在跑**。

一份十几行的 DFS，跑完一个小例子要走七八十步，中间同一行会被十几次不同的调用轮流经过。
只看"当前行高亮"，读者知道执行到第 12 行了，但不知道这是第几层、这一层手里的路径是什么、
弹出来之后会回到谁那里。这是第四章特有的困难，也是这十页动画唯一真正要解决的问题。

78 这一页最后是靠三件事解决的，本文把它们定成整章的硬要求。

## 2. 技术决策

### A. 每一页都必须有"调用链"块

**要求**：任何时候都要能一眼回答"现在这行代码是谁在跑"。

**矛盾**：递归的执行现场天然是一摞栈帧，但代码面板只有一个高亮行，画面上看不出摞了几层。
站里现成的做法是画一张调用栈卡片（第二章几页在用），但那是"有哪些帧"，
不解释"每一帧手里的参数分别是什么"，而第四章参数的传递方式恰恰是全章的考点。

**选择**：每页固定放一张调用链卡片，从最外层到当前层逐层列出，按深度缩进，
每一行写清那一层自己的实参，正在执行的那一层加黑框。

**为什么不只画调用栈**：调用栈只回答"到第几层了"。第四章真正难的是
"同一个路径对象被所有层共用，而起点每层各有一份"，不把每层的实参并排列出来，
这件事永远说不清楚。

### B. 一次调用一种颜色，三处共用同一套色

**要求**：眼睛在代码、调用链、递归树三处之间来回跳的时候，不需要重新对号入座。

**矛盾**：站里通用的语义色是按**状态**分的（当前 / 待处理 / 已完成 / 未访问），
但递归里同一时刻有好几个帧都"活着"，状态色只能告诉你哪个在最上面，
分不出两个同为祖先的帧谁是谁。

**选择**：色板按**调用身份**分，每次调用固定一种底色，代码里的高亮行、调用链里的那一行、
递归树上对应的节点用完全相同的颜色。状态改用别的通道表达：
正在执行的加黑框，子树走完的统一变绿，还没走到的保持灰。

**代价**：这一页偏离了站内"黄=当前"的通用语义。接受这个代价，
因为整章要解决的就是"分不清是谁在跑"，而颜色是唯一能同时覆盖三个视图的通道。
后续九页必须沿用同一套，不要每页自己配色，否则读者每开一页都要重学一遍。

### C. 参数分两类，画面上必须区分开

**要求**：读者要能自己解释清楚，为什么收集答案之前必须先拷一份。

**矛盾**：所有参数在签名里长得一模一样，看不出哪个是所有层共用的同一个对象、
哪个是按值传下去每层各有一份。而这正是这一章最容易写错的地方：
不拷就存，存进去的东西会跟着后面的回溯一起变。

**选择**：调用链的每一行，共用的对象只写名字不写值（写了就是把同一份东西抄四遍，
反而暗示每层各有一份），按值传的和每层自己的局部变量写具体数值，
卡片下面用一句话点明哪些是共用的。

### D. 例子要小到树画得下，画不下就别画树

**要求**：递归树是这一章最值钱的画面，一眼能看出"每个节点就是一个答案候选"。

**矛盾**：通用规则要求优先用力扣官方示例，但组合类题目的官方示例展开之后节点数差得很远。
实测（节点数 = dfs 被调用的次数）：

| 题 | 官方示例 | 节点数 | 结论 |
|---|---|---:|---|
| 78 Subsets | `[1,2,3]` | 8 | 直接用 |
| 90 Subsets II | `[1,2,2]` | 6 | 直接用 |
| 77 Combinations | `n=4, k=2` | 11 | 直接用 |
| 17 Letter Combinations | `"23"` | 16 | 直接用 |
| 46 Permutations | `[1,2,3]` | 16 | 直接用 |
| 47 Permutations II | `[1,1,2]` | 9 | 直接用 |
| 113 Path Sum II | 官方那棵树 | 9 | 直接用 |
| 39 Combination Sum | `[2,3,6,7], 7` | 28 | 太大，缩成 `[2,3], 6`（9 个） |
| 40 Combination Sum II | `[10,1,2,7,6,1,5], 8` | 47 | 太大，缩成 `[1,1,2,5], 6`（12 个） |
| 216 Combination Sum III | `k=3, n=7` | 96 | 缩到最小仍有 31 个，见下 |

**选择**：以 20 个节点为界。20 以内画完整的静态树，坐标写死成常量。
超过 20 的先换小例子，并在页面上注明这是缩小过的例子、官方示例是什么。

216 是唯一一个换了例子也压不下来的：它每一层都要从 1 循环到 9，树天生就宽，
最小的可用例子也有 31 个节点。这一页不画完整树，只保留调用链，
外加一条"当前这一层试到第几个候选"的进度条。

## 交付物

十页动画，每页打开后不用读任何说明文字，光靠点 Next 就能看出三件事：

1. 现在这行代码是第几层调用在跑，那一层手里的参数分别是什么；
2. 哪些参数是所有层共用的同一个对象，哪些是每层各有一份；
3. 递归树上每个节点对应一个答案候选，答案的收集顺序就是这棵树的先序遍历。

**怎么验**：每页都按通用规则先把步骤序列抽出来跑断言（答案对不对、行号合不合法、
执行轨迹连不连续），再在浏览器里点几步看画面。第四章额外多两条：

- 随便停在某一步，调用链的层数要跟递归树上被染色的节点数完全一致；
- 代码高亮行的底色、调用链最下面那一行的底色、树上带黑框那个节点的底色，必须是同一种颜色。

| 快照之间互相串改 | 路径和结果都是会被反复改的数组，快照里存了引用 | 每一步存深拷贝，渲染函数只读快照不写状态 |

## Appendix - 落地细节（第一遍可以跳过）

### 从 78 那一页直接抄的东西

| 抄什么 | 位置 |
|---|---|
| 页面骨架、脚本加载顺序 | `78-subsets.html` 开头到 `renderCodeBox` 那一段 |
| 调用身份色板 `CALL_TINT`（8 色）+ `tintOf()` | 常量区；题目候选多于 8 个时按需扩展，色相要拉开 |
| 调用链渲染 `renderChain()` + `.call-chain` / `.chain-row` 样式 | 原样搬，只改行文案里的参数名 |
| 高亮行染色 `tintLine()` | 原样搬。注意它要在 `highlightLine()` **之后**调用，因为那个共用函数会重置所有行 |
| 递归树 `renderTree()` + 写死的 `NODES` / `POS` | 每题重算坐标：叶子按左到右排格子，内部节点取首尾子节点中点，纵坐标按深度 |
| 步骤生成 `buildSteps()` 的形状 | 真跑一遍算法，每行 `snap(line, info)`；栈帧存 `{ id, index, i }`，快照存深拷贝 |

### 行号表

每页都要按自己的代码重编一份 `const L = {...}`，注意空行也占号。
调用行（发起 + 返回）和循环头（每轮 + 取空）都要在注释里标出来会被走两次以上。

### 状态表达的通道分配

| 通道 | 表示什么 |
|---|---|
| 底色 | 是哪一次调用（身份，不是状态） |
| 黑色描边 | 正在执行这一行的那一帧 |
| 绿色填充 | 子树已经走完，答案已收进结果 |
| 灰色填充 | 还没访问到 |
| 蓝色连线 | 根到当前帧的那条链，也就是调用栈 |

### 例子的写法

缩小过例子的页面（39 / 40 / 216），在页头副标题里写明：
用的是什么输入、官方示例是什么、为什么换（树太大）。不要偷偷换掉不说。
